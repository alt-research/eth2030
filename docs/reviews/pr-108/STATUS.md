# Actual moving-head cold synchronization in progress

A fresh empty-database Native EL (8896b32b) peers with unchanged archival Geth, while a fresh validator-free Lighthouse checkpoint client imports the real live chain optimistically and drives actual Engine forkchoice targets. The EL repeatedly fetches independent headers/bodies while the first observed execution head is still genesis. Source tracing shows that every changed CL target cancels and discards the full backward ancestry walk before it can reach an execution-validated ancestor under sustained updates. The original no-peer/short-chain tests do not prove long moving-target progress. An explicit fixed-target causal control is retained separately and is not relabelled as an automatic moving-target pass.

EIP-3675 keeps target selection with the driving CL, and the selected Engine API keeps SYNCING until execution is actually validated. The correction must preserve immediate replacement/stop cancellation, keep all staged data separate from chain validation/canonical publication, and bound both header count and body bytes. Existing go-ethereum LRU implementations are preferred over a new cache framework. No runtime switch or consensus-rule relaxation is introduced.

A later observation establishes that the original localhost run does eventually finish automatically: execution head 5758 is already synchronized before the planned fixed-target control stops its observer CL. That control is explicitly classified as not exercised and proves no causal improvement. The original long run therefore demonstrates functional cold synchronization; its repeated downloads motivate a separate delayed-fetch/continuous-target consumer to establish the amplification/starvation condition without overstating the live result. The observer is resumed and its actual historical readback remains to be qualified.

The deterministic consumer nominates a newer actual hash-linked test head after every two completed fetches. The original worker makes no execution progress until all 384 updates stop and performs 1,280 downloads. The corrected worker retains completed, hash-checked header records and canonical block bytes across immediate target cancellation. It reaches execution validation while changes are still active. Staged data stays outside the chain and never becomes a validation marker or forkchoice authority; synchronous target replacement and joined stop behavior remain unchanged.

Header records use go-ethereum's existing count-bounded LRU (65,536 entries), and immutable canonical body RLP uses its byte-bounded LRU (64 MiB including hash keys). The explicit single-value size guard closes the upstream cache's permitted oversized-item exception. Backward walking retains lightweight hash/parent/number records, while forward validation refetches an evicted body as necessary. It never needs to retain all block bodies in the ancestry slice. Tests verify eviction/refetch, exact body reuse after the source disappears, byte/count bounds, oversized entries and the separation of download availability from execution validity.

Three executed mutations discard transfer reuse, remove the strict byte guard or treat staged headers as validated; each fails an executed assertion, then source is restored. All 216 full package suites, 22 affected race suites, 45 tagged core/p2p/sync integration suites, full vet and the native-node build pass. The later actual cold application readback succeeds through seven original transactions before an unrelated old Native node exceeds its 15-second historical-state query timeout; that trace is retained in PR 101 and is not attributed to the fresh peer sync. Actual optimized cold-sync qualification remains pending after this separate review is published.
