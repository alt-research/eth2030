# FileDB recovery in progress

The original independent cold full-sync observer reaches the common live chain. Its clean offline history upgrade then spends minutes in FileDB opening/recovery before publishing the first history root. The original 30 MiB WAL is replayed through writeDataFile for every committed operation, including exact already-materialized values and repeated canonical pointers. Each redundant operation creates, fsyncs and renames a temporary file. This is storage recovery work before EVM/index execution; a longer RPC deadline is not a correction.

The proposed correction retains the original WAL commit point, exclusive opening, content values, atomic publication and failure fencing. Only the last committed operation for each key is required to recover the final database state. Exact materialized values may be reused, with the existing recovery directory sync still required before journal truncation. Missing/corrupt files must be repaired. Every truncated or unknown suffix must still preserve the preceding complete committed transactions. No network data is trusted, no validation marker is invented and no consensus hash is changed. This review is separate from PR 109's authenticated history format.
